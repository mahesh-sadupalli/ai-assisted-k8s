Day 1 — Foundations

Before we write a single line of code, we build the mental model. Every section answers three questions: what it is, why we need it, and how it works.

The goal of the project0

Let's be completely clear about what we are building and why, in plain language, before anything else.

What we are building

A self-service platform called Sentinel. A developer sends one request — "please run my service" — and the platform deploys it onto a cluster of machines, keeps it running, watches its health, and, when something breaks, an AI agent reads the logs and metrics and explains what went wrong and what to do about it.

Think of a large office building. Developers are tenants who want to move in (deploy their app). The control-plane is the front desk that takes the request and checks the rules. Kubernetes is the building's operations crew that actually runs everything day to day. Observability is the CCTV and sensors watching every room. The AI agent is a smart guard who watches all those sensors so that, when a pipe bursts, it tells you "pipe burst in room 3, here's how to shut the valve" — instead of you personally watching 200 cameras.
Why this project is relevant

We are aiming at an infrastructure / observability platform engineering role (Grafana Labs and similar). That kind of team wants an engineer who can write real backend services in Go, run them on the cloud with Kubernetes, watch them with observability tools, and — increasingly — use AI to help operate them. Instead of doing five disconnected tutorials, we build one system that touches all of it. That is a far stronger thing to show than a pile of unrelated exercises.

How it works, end to end
One request flows left to right; the AI agent watches the whole thing and closes the loop back.

In one sentence: a developer asks → the Go control-plane validates and forwards it → Kubernetes runs it on AWS → observability watches it → the AI agent turns raw signals into a plain-English diagnosis. Everything in Day 1 below is one piece of this picture.

Why Go, not Python?1

You already know Python. So the first honest question is: why learn a second language at all?

What Go is

Go (also called Golang) is a programming language created at Google to build fast, reliable servers and command-line tools. It is compiled and statically typed — two words we'll unpack in a second.

The key idea: compiled vs interpreted

This is the difference that explains almost everything else.

  • Python is interpreted. Another program (the Python interpreter) reads your code line by line while it runs. Flexible and quick to write, but slower to execute, and the machine needs Python installed to run it.
  • Go is compiled. A compiler translates your whole program into raw machine code ahead of time, producing a single file (a "binary"). It runs fast and needs nothing else installed — not even Go.
An analogy: Python is a live interpreter at a meeting, translating each sentence as it's spoken — flexible, but there's a person in the loop every time. Go is a fully translated book, printed once — you hand someone the book and they read it at full speed with no translator present.
Why we need Go here specifically
  • It is the native language of cloud infrastructure. Kubernetes, Docker, Terraform, Prometheus, and Grafana are all written in Go. To work on infrastructure platforms, Go is the language the whole field already speaks.
  • It's perfect for containers. A Go program compiles to one tiny self-contained binary. That makes a container image small, and the service starts in milliseconds using little memory.
  • Concurrency is built in. Handling thousands of requests at once is native to Go (we'll meet "goroutines" later). A control-plane API needs exactly this.
  • Static typing catches mistakes early. Types are checked when you compile, so many bugs are caught before the program ever runs — safer for production services.

The cloud & why AWS2

Everything we build runs "in the cloud". So: what is that, really, and why AWS?

What "the cloud" is

The cloud is simply renting other people's computers over the internet, instead of buying and running your own. A provider owns huge data centers full of machines; you rent exactly what you need, for as long as you need it, and pay for usage. When you're done, you give it back and stop paying.

An analogy: owning servers is like buying a car — big upfront cost, you maintain it, it sits idle most of the time. The cloud is like a taxi/rental — you summon a car when you need one, pay per trip, and never worry about parking or repairs.
Why we need it
  • No upfront hardware. You get a cluster of machines in minutes, not weeks.
  • Elastic. Need 10 machines today and 100 tomorrow? Scale up and back down; pay only for what ran.
  • Managed services. The provider runs the hard parts for you — including managed Kubernetes, which we'll use.
Why AWS specifically
  • It's the biggest, most in-demand provider. Most infra job postings list AWS. It's the safest bet for the résumé.
  • It has managed Kubernetes (a service called EKS), so we don't have to run the hard bits of Kubernetes ourselves.
  • You already have some AWS and Terraform background — we build on what you know.
The AWS services we'll actually touch

One more idea: regions

AWS has data centers all over the world, grouped into regions (for example eu-central-1 is Frankfurt). You pick a region close to your users. Each region is split into isolated availability zones for resilience — if one zone has a problem, the others keep running.

Reference AWS Cloud101 (in your Books/AWS/Cloud101) — skim the "what is cloud / regions / core services" material. Your Navigating Linux PDF is worth having open too, since the servers you rent run Linux.

How we access AWS3

You rented the machines — now, concretely, how do you actually reach and control them?

First: identity (IAM)

Everything in AWS is gated by IAM (Identity and Access Management). When you create an account you get a root user — all-powerful, and you almost never use it. Instead you create IAM users and roles with only the permissions they need. This is the principle of least privilege: give each identity the smallest set of powers that gets the job done.

Three ways to interact with AWS
Same AWS underneath — three ways in. Console to learn and look, CLI to automate, Terraform to build repeatably.
  • Web Console — a website where you click to create things. Best for learning and looking around.
  • AWS CLI — type commands like aws s3 ls in your terminal. You configure it once with aws configure, giving it an access key (an ID + secret) tied to an IAM user. Best for automation.
  • Terraform (Infrastructure as Code) — you describe the infrastructure you want in files, and Terraform creates it. Repeatable, reviewable, and the way real teams work. This is our path for M3.
Reaching an actual server: SSH

When you rent a virtual server (an EC2 machine), you get into its terminal with SSH (Secure Shell) — an encrypted remote login. You hold a private key file; the server holds the matching public key; only you can connect:

# connect to a Linux server by its address, using your key
ssh -i my-key.pem ec2-user@203.0.113.42

A security group acts as the server's firewall — it decides which ports are open (for SSH you open port 22, and only to trusted addresses).

Golden rule about secrets: access keys and .pem key files are like passwords. Never commit them to git or share them. Our .gitignore already blocks *.pem and credentials for exactly this reason.
Reference AWS Cloud101 for IAM/console basics; the AWS CLI "getting started" docs for aws configure. SSH and the Linux terminal: your Navigating Linux PDF.

Docker & containers4

Before Kubernetes can run our service, the service has to be packaged as a container. This is what Docker does.

The problem it solves

Software depends on its surroundings — a specific language version, certain libraries, particular settings. Move it to another machine where those differ, and it breaks. This is the famous "but it works on my machine" problem.

What a container is

A container packages your app together with everything it needs — runtime, libraries, config — into one sealed, isolated unit. That unit runs identically on your laptop, a colleague's machine, or a server in AWS, because it carries its whole environment with it.

An analogy: a shipping container. Before them, loading a ship meant hand-stacking barrels, sacks and crates of every shape. The standard steel container changed everything: seal your goods inside one standard box, and any ship, crane, or truck in the world can handle it without caring what's inside. A software container does the same for programs.
How it works
Write a Dockerfile once → build an image → run as many containers as you like → store the image in a registry.

Kubernetes5

You can run one container by hand. Running many, reliably, across many machines — that's what Kubernetes is for.

The problem it solves

A single container on one laptop is easy. But a real system needs much more: many copies of a service to handle load, automatic restart when one crashes, rolling updates with no downtime, spreading across machines so one failure doesn't take everything down, and networking so the pieces can find each other. Doing all that by hand, around the clock, is impossible.

What Kubernetes is

Kubernetes (often written "K8s") is a system that runs and manages containers across a group of machines automatically. Its trick is desired state: you declare what you want ("keep 3 copies of my app running"), and Kubernetes continuously works to make reality match — restarting, rescheduling, and healing on its own.

An analogy: if containers are standardized shipping boxes, Kubernetes is the fully automated port — the cranes, the scheduling, the tracking system — that decides which ship carries which box, reloads instantly if one falls, and keeps the whole harbour flowing without a human directing each crane.
How it works — the core objects
ObjectWhat it is
PodThe smallest unit — one (or a few tightly-linked) containers running together. Pods are disposable; they come and go.
DeploymentManages Pods for you: "keep 3 replicas alive, and roll out new versions safely."

You talk to Kubernetes with a command-line tool called kubectl, usually by giving it YAML files that describe the desired state. In Milestone 2 you'll run a small cluster on your own laptop for free using a tool called kind, and deploy your first Pod.

Where AWS comes back in: running the Kubernetes "brain" (its control plane) yourself is fiddly. EKS is AWS's managed Kubernetes — AWS runs that brain for you, and you just add worker machines and deploy. That's our Milestone 3.
Reference kubernetes.io/docs/concepts — read "Pods", "Deployments", and "Services". This is the one area with no book on your shelf, so the official docs are the reference (they're excellent).

LLMs & AI agents6

This is your differentiator — the part most infra candidates don't have. Let's ground it from first principles.

What an LLM is

An LLM (Large Language Model) does one core thing: given some text, it predicts the next chunk of text, over and over, until it decides to stop. That chunk is called a token — roughly three-quarters of a word (the word "Kubernetes" is about three or four tokens). Everything you send in and everything it sends back is counted in tokens — and tokens are what you pay for.

Tokens in, tokens out. You talk to it over a simple HTTP API, sending a list of messages.
What turns an LLM into an "agent"

A plain LLM just talks. An agent is an LLM that can use tools in a loop. You hand it a set of tools (functions it may request — "read these logs", "fetch this metric"). It cannot run anything itself; instead it asks you to run a tool, your code runs it, and you feed the result back. It keeps going until the task is done.

The model decides what to do; your code decides whether and how to do it. That control point is where safety lives.
Why it belongs in this project

When a service breaks, a human normally reads pages of logs and metrics to figure out what happened. An agent can read those raw signals and hand back a clear "this is what broke, this is the likely cause, this is what to try" — shrinking the time from "alarm goes off" to "human understands the problem". That is directly what an observability-platform team values.

Safety, from day one: in the early milestones the agent only reads and explains — it changes nothing. Any power to actually act comes much later, and only behind a human-approval step with a full audit log. Read-only first is the safe path.
Reference Raschka, Build a Large Language Model (From Scratch), Chapter 1 and the start of Chapter 2 (what a token is). Hands-on LLM for the agent/tool-use idea.

How it all fits together7

Now let's connect the pieces you just met into one clear story.

Follow one service on its journey through Sentinel:

  • Go — you write the control-plane API in Go, because that's the language of cloud infrastructure and it compiles to a tiny, fast binary.
  • Docker — you package that Go binary into a container image, so it runs the same everywhere.
  • AWS — you rent the machines to run it on, using IAM for access and Terraform to build the infrastructure.
  • Kubernetes (EKS) — AWS's managed Kubernetes runs your container reliably: many copies, auto-restart, safe updates.
  • Observability — Prometheus and Grafana watch the running service's metrics and logs.
  • The AI agent (Python) — reads those signals and turns them into a plain-English diagnosis, with a human in the loop.

Each Day 1 topic is one link in that chain. You don't need to master all of them today — you need the map, so that when we build each piece, you know exactly where it sits and why it's there. That's the whole point of a foundations day.

The one-line summary: we write a service in Go, box it with Docker, run it on AWS via Kubernetes, watch it with observability tools, and let an AI agent explain it when it breaks.

Test yourself8

Answer each in your own words first. If you can't, that section is worth re-reading — that's the signal we're looking for.

Q1 In one or two sentences, what is Sentinel and who is it for?
A self-service platform that lets a developer deploy a service with one request; it runs the service on Kubernetes, watches its health, and uses an AI agent to explain problems and suggest fixes. It's built to demonstrate infra + observability + AI skills for a platform-engineering role.
Q2 We already know Python. Give two concrete reasons we're using Go for the control-plane service.
Any two of: (1) Go is the language of cloud infra — Kubernetes, Docker, Terraform, Prometheus, Grafana are all written in it; (2) it compiles to one tiny self-contained binary, ideal for small, fast-starting containers; (3) concurrency is built in, perfect for a server handling many requests; (4) static typing catches bugs at compile time.
Q3 What is "the cloud" in plain terms, and what does IAM control?
The cloud is renting someone else's computers over the internet, paying for what you use. IAM (Identity and Access Management) controls who is allowed to do what in AWS — identities and their permissions. Use least privilege; avoid the root user for daily work.
Q4 Name the three ways to interact with AWS, and how you get into an actual EC2 server's terminal.
Web Console (click), AWS CLI (aws ... commands), and Terraform (infrastructure as code). You reach a server's terminal with SSH using a private key: ssh -i key.pem ec2-user@<ip>, with port 22 opened by its security group.
Q5 What's the difference between a Docker image and a container? What problem do containers solve?
An image is the frozen template, built once; a container is a running instance of it (you can run many). Containers solve the "works on my machine" problem by bundling the app with its whole environment so it runs identically everywhere.
Q6 Why do we need Kubernetes if we can already run a container? Give two things it does for us.
Running one container is easy; running many reliably is not. Kubernetes automates it: any two of — keep N replicas alive, auto-restart on crash, roll out new versions safely, spread across machines, and provide stable networking. You declare the desired state; it maintains it.
Q7 What makes an LLM an "agent", and who actually executes a tool when the agent wants to use one?
An agent is an LLM that can use tools in a loop. When it wants a tool, it only asks — your code executes it and feeds the result back. That control point is where logging, approval, and safety live.
